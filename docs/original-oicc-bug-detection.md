已阅读项目指南、[原工具功能核对](oicc-comparison.md)、[当前生成契约](openoicc.md)，并回查任务中提供的 2026-10-11 OIOIC 核心安全审查报告。原 oicc 没有随附工具源码，因此不能给出其内部函数的源码行号；下文分别使用生成文件行号、二进制文件偏移及复现命令定位。二进制偏移是文件偏移，不是运行时地址。

核查对象信息：

- 帮助显示版本：`oicc 1.0.18`，`August 2011`。
- 文件格式：PE，Machine 为 `0x014c`（x86）；执行环境为 Windows x86_64。本轮未执行原 Linux 程序。
- 可执行文件 SHA-256：`883246670eb604d2ab1a658ed9bf1518962cee8fd1f6feb5e9b075597bf9ca3e`。

证据分为三类：“运行复现”表示实际观察到行为；“生成源码静态确认”表示从本次实际创建的文件中确认危险路径；“二进制模板线索”表示发现模板片段，但尚未获得成功的完整构造输出，不能据此断言所有生成分支都存在同样问题。

所有修复方案均为建议，未应用到原程序或上游源码。涉及历史类型的代码为原片段节选；建议优先遵循当前 NEOioic 的安全契约，不直接混用新旧接口。

## 1. 自身创建的宿主目录无法完成构造，持续报告 E0018

### 1、代码位置

原程序的目录构造入口。内部文件打开函数和路径拼接实现未知。

复现输入为原程序刚创建的 `mo/Demo/`；目录采用普通 ASCII 名称，无需使用带空格路径或当前 NEOioic 示例。

### 2、问题内容

在新的可写工作目录中执行：

```text
oicc mo Demo
```

返回 0，输出 `Creating...`、`Ok.`，创建宿主、节点和 Main 文件。随后切换到生成的 `mo/Demo/`，执行无参数的 `oicc`，得到：

```text
Constructing...
error E0018: can't open strm_nodestru file.

Failed.
```

从初始工作目录显式传入生成宿主的完整路径，结果相同。两次失败的进程退出值在本机 Python 中均为 `4294967295`（`0xffffffff`）。对工作目录内已有文件进行前后 SHA-256 比较，未发现新增、修改或删除文件。

这说明当前环境中，“创建骨架 → 目录构造”的正常操作链无法完成，也阻断了原构造器输出的差分验证。该错误发生在原工具自己的输出上，不能仅归因于当前 NEOioic 的 API 更名。

证据等级：运行复现；根因未确认。尚不能区分临时文件路径错误、文件访问方式问题、缺少未记录的外部资源或其他环境要求，不能直接断言是权限漏洞、内存错误或所有 Windows 环境均无法使用。

### 3、修复方案

在文件打开失败处报告实际文件路径、操作类型和系统错误码，区分输入不存在、临时文件创建失败及访问被拒绝。核对默认目录和显式目录两条路径的工作目录处理；临时文件应创建在明确、可写的位置，不依赖未说明的安装文件或进程启动目录。

回归至少覆盖自身新建宿主、当前目录调用、显式相对/绝对目录、空格路径及只读目录。若构造需要用户先配置特定文件，应给出该文件名与配置要求，不能只暴露内部流变量名 `strm_nodestru`。

复核：已确认故障表现，未确认内部根因；本次没有观察到失败导致源文件损坏。

## 2. 生成宿主在外部存储对象 OID 耗尽时解引用 NULL 输出参数

### 1、代码位置

本次 `oicc mo Demo` 实际生成的 `mo/Demo/ho.c:94–96`、`119–141`，关键解引用在第 129 行。该文件 SHA-256 为 `2774940f0c37e304b992ece7f50aaf85c5a3477e71207998c093afef8f254f22`。

```c
assert( !(NULL == ppObj && NULL == pExotic) );
assert( !(ppObj != NULL && pExotic != NULL) );
/* 构造成功后，OID 低位发生回绕。 */
}else if((MSKSO & gs_tad.oid) < (MSKSO & oidbak))
{
	gs_tad.oid = oidbak;
	pem = (EM_OIOIC*)GetEMofBN(*ppObj, MSN_OIOIC);
	/* 清理队列后才区分本体所有权。 */
	if(NULL == pExotic)
	{
		free(*ppObj);
		*ppObj = NULL;
	}
	return RN_LACKOID;
}
```

### 2、问题内容

模板明确允许并要求外部存储组合 `ppObj == NULL`、`pExotic != NULL`。若用户补充的构造器成功推进 OID 并跨过节点编号低位边界，耗尽清理分支仍先执行 `*ppObj`，因此在合法参数组合下解引用 NULL，本应返回 `RN_LACKOID` 的失败路径变成崩溃风险。

该问题来自原工具实际生成的宿主模板，不只是历史示例中的手写代码；对应既有安全报告第 11 项。未配置业务分支的初始骨架不会到达这一路径，触发还需要可成功创建的对象模型和接近耗尽的 OID。

证据等级：生成源码静态确认；本轮未编译旧 API 宿主或动态触发 OID 耗尽。

### 3、修复方案

构造成功后先根据 `pExotic` 选择实际对象地址，再访问根成员。外部存储失败时清理并置空队列，本体由调用者管理；动态存储失败时才释放本体并清空输出指针。

更稳妥的做法是在构造前验证或预留足够的节点 OID，避免成功构造后才发现编号回绕。若仍保留事后清理，必须同时验证动态和外部存储路径。

复核：危险解引用发生在区分外部存储之前；不能仅给 `free(*ppObj)` 增加条件而遗漏前面的 `GetEMofBN(*ppObj, ...)`。

## 3. 构造模板使用数组前一位置表示空队列

### 1、代码位置

上述 SHA-256 二进制文件内的 ASCII 模板片段：文件偏移 `0x149a0`（输出队列）、`0x14bf8`（输入队列）。

```c
((EM_OIOIC*)(pND->pEM))->OQ.Front =
	((EM_OIOIC*)(pND->pEM))->OQ.Rear =
	((EM_OIOIC*)(pND->pEM))->OQ.Dtrm - 1;
```

输入队列有对应的 `IQ.Dtrm - 1` 片段。

### 2、问题内容

若这些片段用于分配成功后的队列初始化，`Dtrm` 指向分配区首元素，形成 `Dtrm - 1` 本身就不符合 C 指针运算规则，不以是否解引用为条件。问题不依赖当前 API 名称，也不能通过“实际运行没有崩溃”排除。

这对应既有安全报告第 1 项的构造器部分。运行时的入列、出列或重置问题不能仅凭该片段一并归因于生成器；它们需要独立检查对应运行时。

证据等级：二进制模板线索。已确认原程序包含上述初始化文本，未通过本轮成功生成完整构造器确认其实际使用分支，也未运行该模板产物。

### 3、修复方案

采用当前 NEOioic 的空队列 `Front/Rear == NULL` 契约，容量零表示禁用；有数据时指针处于有效数组内。同步调整运行时队列算法，先计算合法整数偏移再形成指针，避免只改构造模板造成运行时表示不一致。

复核：这里报告的是模板中的非法哨兵线索，没有声称原工具自身的内部队列使用了同样实现。

## 4. 构造模板的席位乘法、字段赋值和总尺寸存在溢出或截断风险

### 1、代码位置

二进制文件偏移 `0x14e24`、`0x15324`，以及 `0x15100–0x154a0` 区间内的总量模板片段：

```c
pND->NCS = NumCR * %s;
p += sizeof(VR) * pND->NCS;

UI32   ux_CS = NumCR * %s;
UI32  sum = ux_ND * sizeof(OBJECT)
	/* 后续拼接 AIB、ABN、ACS 和成员块尺寸。 */
```

构造函数签名中 `NumCR` 声明为 `SI32`。`%s` 是原二进制中的格式占位符，不是已成功生成的具体常量。

### 2、问题内容

这些模板将席位数量直接写入节点字段，并用 `UI32` 接收总尺寸，而非统一使用 `size_t` 和显式边界检查。若席位倍数替换为普通有符号整数常量，乘法会先按操作数类型运算；事后赋给较宽的变量不能补救已经发生的有符号溢出。若目标字段比乘积窄，还可能出现分配布局与登记容量不一致。

此外，包含 `sizeof` 的尺寸表达式最终写回较窄整数类型时，在大布局上可能截断，导致实际分配空间不足。这对应既有安全报告第 8 项。

证据等级：二进制模板线索。原模板中确有上述表达式，但本轮没有完整输出、全部历史类型定义和控制流，不能排除其他位置存在提前检查，也没有在原工具产物中复现具体截断值。既有安全报告对历史示例的故障注入结果不能当作本轮对原二进制的运行验证。

### 3、修复方案

先按所有节点的最大席位倍数检查字段可表示范围，再转为 `size_t` 做乘法；每次尺寸相乘和累加都检查 `SIZE_MAX`。分配总量和各节点登记容量使用同一份已校验计算结果，不允许隐式窄化。

补充生成产物的边界验证，包括最大合法容量、首次超限容量、多继承最大倍数和大尺寸布局；拒绝时不分配、不消耗 OID、不写调用者存储。

复核：尚需取得完整原输出核对检查是否缺失；当前确定的是存在需要检查的危险模板表达式。

## 5. 成员块按裸 sizeof 推进，后续布局可能失去对齐

### 1、代码位置

二进制文件偏移 `0x14908`、`0x14de8`：

```c
pND->pEM = (EM*)p;
p += sizeof(EM_%s);
```

### 2、问题内容

`sizeof` 只保证该类型的数组元素可以连续排列，不能保证任意成员块后面紧接的指针数组、访问记录或下一个节点成员仍满足各自对齐要求。例如一个大小为 1 的成员结构，可能把后续指针字段布局的起始地址推进到非对齐位置。

在需要严格对齐的平台上，按未对齐地址访问对象会产生未定义行为；x86 平台允许部分未对齐硬件访问也不能证明 C 层面正确。该问题与前项的整数溢出不同，布局很小时也可能出现。

证据等级：二进制模板线索。已确认裸 `sizeof` 推进片段，尚未取得完整构造输出检查它后面是否另有对齐补偿，也没有运行严格对齐平台产物。此项对应本项目已记录的 NEOioic 成员块对齐要求及历史构造修复范围。

### 3、修复方案

布局时对每个块的起始偏移进行对齐检查或向上对齐，并检查补齐过程溢出。当前 OpenOICC 使用 NEOioic 对齐规则并明确拒绝超出布局能力的成员类型；不能只给成员结构加对齐属性而保留原偏移计算。

复核：没有把历史输出未使用当前宏名本身视为缺陷；关注的是实际布局是否满足所存放类型的对齐。

## 6. 外部存储模板未见与 calloc 等价的整体初始化

### 1、代码位置

二进制文件偏移 `0x15164`：

```c
BYTE*  pIC = NULL;
if(NULL == pExotic)
{
	*ppObj = NULL;
	pIC = (BYTE*)calloc(sum, 1);
}else
{
	pIC = pExotic;
}
```

### 2、问题内容

该片段中动态分配路径自动清零，外部存储路径直接沿用调用者字节。如果后续只写部分字段，引用计数、空访问席位、根节点基节点字段及禁用队列状态就可能保留旧内容，进而影响登记、关闭和资源释放。生成宿主的说明允许外部存储，不能仅假设它总是静态零初始化内存。

这与既有安全报告第 9 项的历史示例问题一致，但仅凭片段缺少 `memset` 不能证明完整构造器没有逐字段初始化。

证据等级：二进制模板线索，属于待完整输出确认的候选问题。没有将既有报告中的 A5 填充运行结果移植成对原生成器的验证结论。

### 3、修复方案

在容量和对齐前置条件满足后，建立任何节点或队列前清零整个构造区；或者逐字段完整初始化并用测试证明与动态路径等价。接口应明确外部存储的容量、对齐、有效期，以及不能覆盖仍持有资源的活动对象。

复核时使用足够大且正确对齐、预填非零字节的存储，检查整个对象图，再实际执行打开、访问、关闭和外部资源清理；不能只检查构造函数的成功返回值。

## 7. 正常帮助请求返回非零退出码

### 1、代码位置

原程序命令行帮助入口；内部返回语句位置未知。复现命令为 `oicc -h`。此前功能核对也观察到 `-help` 返回相同帮助。

### 2、问题内容

本次 `-h` 完整显示帮助，未报告用法错误，但进程退出码为 1。同一次核查中，正常创建宿主返回 0，重复名称和保留名称错误返回 `0xffffffff`。

这会使按“非零即失败”处理的脚本或 CI 将正常帮助查询视为失败，需要额外适配。不过原帮助未明确约定退出状态，因此应归类为命令行可用性与自动化一致性问题，而不是内存安全漏洞或已证实违反其书面契约的缺陷。

证据等级：运行复现；是否为原作者有意设计未知。

### 3、修复方案

正常帮助和版本查询返回 0；非法参数和执行失败返回非零，并在帮助中记录退出码约定。若保留历史约定，至少应明确说明，避免用户根据正常工具惯例误判。

复核：退出码异常不代表帮助文本不正确，也不证明创建或构造成功时的退出码同样错误。
